MiniRank — Development Process

How the project was planned, built and refined with opencode

1. Plan

The plan we followed and the key decisions we locked in.

The project is a keyword position tracker (MiniRank): a small full-stack app in which the user tracks daily simulated search-engine positions for a set of keywords. It was built one requirement at a time, and each requirement was implemented, tested and committed before moving to the next one.

The requirements, in order

#RequirementWhat it delivered
M1CRUD for keywordsAdd, edit and delete tracked keywords with a simple UI
M2Seed script6 demo keywords with ~30 days of simulated positions (1–100)
M3Refresh positionsOne-click refresh that generates today's ranks and updates the list via AJAX, no page reload
M4List + trend + searchCurrent position, 7-day trend (Improved / Declined / Stable) and text search
M5Detail pageFull position history per keyword, later extended with an SVG chart and CSV export
M6Security auditReviewed every query and output: parameterized SQL + escaped HTML everywhere
M7READMESetup, commands, project structure and security documentation
M8Responsive UITable collapses to cards on small screens; theme and layout polish
+User accounts & CSRFRegister / login / logout with hashed passwords, sessions and CSRF protection
+DockerOne-command start of the app and database in a container
+Automated testsPHPUnit suite (16 tests) running against an in-memory SQLite database

How we worked

  • Requirement by requirement. Each step was small enough to be implemented and committed on its own, so progress was always verifiable.
  • Testing before moving on. Every step was checked manually in the browser (and with the automated suite once it existed) before the next requirement started.
  • The user writes the commits — one commit per implemented requirement, so the history mirrors the plan.

Key decisions

  • Locked stack: PHP 8+, SQLite, PDO, HTML/CSS/vanilla JS — no frameworks, libraries or build tools.
  • Simulated ranking data. Never use an external search-engine API; positions are generated server-side.
  • Clean separation: database access (repositories), business logic (RankingService) and presentation (views) kept apart.
  • Security first: PDO prepared statements everywhere, HTML escaping on every output, bcrypt password hashes, per-session CSRF tokens on every form and the AJAX request.
  • Shared dataset, login only: accounts gate access to the app, but keywords are not split per user.
  • Keep logic as simple as the requirement asks: the trend ended up as a simple "today vs 7 days ago" comparison (see the fixes below).
  • No chart library: the detail-page chart is hand-rolled SVG to avoid adding a dependency.
  • One Docker container: SQLite is embedded, so the "database" is a file on a persistent volume — no separate database server container.
  • Tests never touch real data: PHPUnit runs against an in-memory SQLite database.

2. Prompts & Fixes

Three real prompts from the sessions — including one that failed — and the mistakes that had to be corrected.

Prompt 1 — Trend calculation worked, then simplified

"Add a list view with current position, 7-day trend and search" (requirement M4)

The first implementation calculated the trend with a 7-day window average (average of the last 7 days vs. the previous 7 days). It worked, but it was more complex than the requirement asked for and made the logic harder to reason about and test.

Fix: reverted to a simple single-point comparison — current position vs. the position from 7 days ago. Lower is improved, higher is declined, equal or missing is stable. The change was verified with temporary checks and the diff shrank by roughly 70 lines.

Prompt 2 — Docker setup failed at first

"I need for this project to have a docker setup that starts app and database and I need to know how to test it"

The container build and the app worked, but two mistakes needed correcting:

  • Two different localhost URLs. The local dev server ran on port 8000; I exposed Docker on port 8080 to avoid a clash. That left the project with two URLs (localhost:8000 vs localhost:8080), which was confusing. After the user asked to unify on one port, the mapping was changed to 8000:80 so Docker serves on http://localhost:8000 — the same URL the app always used.
  • Wrong PHPUnit version in the image. The build downloaded the latest phpunit.phar (v13), which requires PHP ≥ 8.4, but the container runs PHP 8.2 — running the tests failed immediately with "This version of PHPUnit requires PHP >= 8.4.1". Fixed by pinning phpunit-11.5.phar, the newest line compatible with PHP 8.2.

Minor fixes along the way: a global ServerName to silence an Apache warning, and a .dockerignore so the local development database is never baked into the image.

Prompt 3 — User accounts & CSRF protection worked

"Add user accounts (register, login, logout) with hashed passwords and sessions, plus CSRF protection"

We agreed on a shared dataset, login only: accounts gate access to the app, but keywords are not scoped per user. The implementation included a users table, bcrypt password hashing, hardened sessions (HTTP-only cookies, SameSite=Lax, session id rotation on login), and a per-session CSRF token verified on every mutating request — including a header check on the AJAX refresh endpoint.

The seed script creates a demo account (demo@example.com / demo1234) so a fresh install is usable immediately. Verified with a full HTTP flow (login, logout, rejected bad tokens, protected pages) and the automated suite grew to 16 tests.

3. Retrospective

What I would do differently, and what the whole process cost.

The overall process worked well: building requirement by requirement meant every step was small, testable and easy to commit. The plan was solid from the start.

What I would do differently: from the very beginning, after every step I would ask explicitly "how do I test this new implementation?". Often I finished a feature and then had to figure out on my own how to verify it before committing — that wasted time. If I had asked for a short "how to test" explanation at the end of every step, I could have checked each change immediately and committed it right away.

The port mix-up (two localhost URLs after Docker was added) taught me to keep a single port from the beginning and confirm it whenever something new is introduced. The PHPUnit version failure taught me to pin tool versions instead of grabbing "latest".

How I prepared and what I learned about the tools

I used ChatGPT in two ways. First, to understand the requirements and the candidate brief — that helped me figure out what I actually needed to ask opencode and how to plan my prompts, so each request to the agent was focused on one requirement at a time. Second, during the setup of opencode, git and my PHP IDE: whenever I ran into an error or didn't know what to do next, I asked ChatGPT for help to get unstuck and finish the setup.

The commit history is not perfect: it took me a while to understand how to write and add commits, and some of them I lost along the way. With time I found a rhythm — one commit per requirement with a clear message.

Overall experience

I really enjoyed building this project with the opencode agent — it was my first time ever working this way. Having the agent implement, explain and verify each step made the whole process feel fast and clear.

Time spent

Developing this app with opencode took about 6–8 hours in total. I worked across 3 days, roughly 2–3 hours per day, implementing, testing and committing each requirement.

Takeaways

  • Small, single-purpose requirements are the fastest way to make steady progress.
  • Ask for the test steps up front — don't discover them after the feature is done.
  • Keep logic as simple as the requirement asks; simplify when a feature grows beyond its scope.
  • Pin tool versions and keep a single, consistent URL/port for the whole project.
